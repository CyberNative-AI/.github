# Rust 1.99.0 can return a `false` that C reads as `true`

Rust 1.99.1 (October 15, 2026) fixes [rust-lang/rust#163911](https://github.com/rust-lang/rust/issues/163911). In Rust 1.99.0 (October 1), an `extern "C"` function that returns `bool` can hand its caller a byte that is neither 0 nor 1 on x86-64 Linux and other x86-64 System V targets. The C and Python callers we tested treat any nonzero byte as true, so a `false` becomes `true` on the other side.

The issue shows one function. We built 19 common shapes into one library with 1.99.0 and called each from C with an input whose answer is `false`. In the release build, 10 came back nonzero. All 10 test the lowest bit of an integer.

| Rust body (input gives `false`) | 1.99.0 release | 1.99.0 debug | 1.99.1 |
|---|---|---|---|
| `(flags & 0x1) == 0x1` (`u8`) | **0x10** | **0x10** | 0x00 |
| `x & 1 != 0` (`u8`, `u32`) | **0x10** | 0x00 | 0x00 |
| `x & 1 == 1` (`u64`) | **0x10** | **0x10** | 0x00 |
| `n % 2 == 1` (`u32`) | **0x10** | **0x10** | 0x00 |
| `n % 2 != 0` (`i32`) | **0x10** | 0x00 | 0x00 |
| `(x >> n) & 1 == 1` (`u8`, n = 0) | **0x12** | **0x12** | 0x00 |
| `(*opts).flags & 1 != 0` (struct field) | **0x06** | 0x00 | 0x00 |
| `extern "system" fn`, `x & 1 != 0` | **0x10** | 0x00 | 0x00 |
| callback `extern "C" fn(u32) -> bool` handed to C, `x & 1 != 0` | **0x10** | 0x00 | 0x00 |
| `(x >> 3) & 1 == 1` | 0x00 | **0x06** | 0x00 |
| `x & 8 != 0`, `x == 0`, `a > b`, `n % 2 == 0`, `!b`, `a && b`, `b`, reading a `bool` field | 0x00 | 0x00 | 0x00 |

A gcc-built C caller takes the `true` branch for every bold value, at `-O0` and at `-O2`. In Python, `ctypes` with `restype = c_bool` returns `True` for `is_odd(16)`.

The returned byte is the input with its other bits left in. When the answer is bit 0 of an argument, 1.99.0 returns the argument register as it is: `is_flag_set` and `is_odd` compile to `mov %edi,%eax; ret`, and 1.99.1 adds `and $0x1,%al` ([`results/`](results/)). The x86-64 calling convention requires bits 1–7 of a returned `bool` to be zero, and callers rely on that. The issue thread and the fix ([#163917](https://github.com/rust-lang/rust/pull/163917)) explain why the zero-extension went missing.

## Was your binary built with 1.99.0?

```sh
readelf -p .comment libyours.so | grep rustc
# rustc version 1.99.0 (b940084d7 2026-09-28)
```

rustc writes its version into the `.comment` section. In our builds that line survived cargo's `strip = true`, `strip = true` with fat LTO and `panic = "abort"`, and a C program that statically links the Rust `staticlib` after `strip --strip-all`. If someone removed the section, the standard library's paths usually still carry the compiler commit: 1.99.0 is `b940084d7eb6…`.

```sh
strings -a libyours.so | grep -o '/rustc/[0-9a-f]\{40\}' | sort -u
```

[`scripts/check-binary.sh`](scripts/check-binary.sh) runs both on any `.so`, `.a` or executable, and exits with an error for a file it cannot read. Our results: [`results/1.99.0/binary-checks.txt`](results/1.99.0/binary-checks.txt). In the statically linked C program only the `.comment` line was left.

## Which functions to look at

```sh
rg --type rust -nU '\bextern\s+(?:"(?:C|system|sysv64)(?:-unwind)?"\s+)?fn\s*\w*\s*(?:<[^>{]*>)?\s*\((?:[^()]|\([^()]*\))*\)\s*->\s*bool\b' .
```

This is a heuristic, not a parser. It looks for functions and function-pointer types with a C-family calling convention that return `bool`, including signatures split over several lines. Functions declared inside an `extern "C" { ... }` block are calls into C and are not listed. On this library, a file of awkward signatures and four public Rust projects that export or generate C APIs, it found the same 115 signatures as a separate bracket-matching parser, none missed and none extra ([`results/grep-check.txt`](results/grep-check.txt)). That is agreement on a sample, not proof of coverage: both miss raw identifiers (`fn r#match`). The pattern also misses a function whose parameters nest brackets more than one level deep (a callback that takes a callback), functions generated by macros and a `bool` behind a type alias, and it matches signatures inside comments. A match is a function to read, not a bug. **No match does not mean a library is safe**: if a 1.99.0 build is involved and you cannot rule out a `bool` return, rebuild it. [`scripts/find-bool-exports.sh`](scripts/find-bool-exports.sh) wraps the pattern and exits with an error for a path that does not exist.

## What to do

If a 1.99.0 binary exports any of these functions, rebuild it with 1.99.1 (`rustup update stable`) and ship the rebuild. Do not read the function bodies to decide whether a binary is safe: our table covers 19 shapes, not all of them. The fix concerns `bool` return values. APIs that return `c_int`, `u8` or another integer type instead do not have this bug, and UniFFI passes `bool` as an `i8`.

If you call such a library and cannot get a rebuild yet, read the result as a byte and test bit 0. In Python: `f.restype = ctypes.c_uint8`, then `bool(f(x) & 1)`.

## Method and limits

- Linux x86-64, `rust:1-slim-trixie` (amd64, `rust@sha256:2752b332db73…`, rustc 1.99.0 on October 15). 1.99.1 was installed with rustup in the same image. `scripts/repro.sh` builds the library and the C callers and writes `results/<version>/`:

  ```sh
  docker run --rm --platform linux/amd64 -v "$PWD":/w:ro -v "$PWD/out":/out rust:1-slim-trixie sh /w/scripts/repro.sh          # 1.99.0
  docker run --rm --platform linux/amd64 -v "$PWD":/w:ro -v "$PWD/out":/out rust:1-slim-trixie sh /w/scripts/repro.sh 1.99.1   # 1.99.1
  ```

  The `rust:1` tag will move to newer releases; check `rustc -vV` in `out/<version>/` before comparing. `scripts/ctypes_check.py` ran with Python 3.12 on Ubuntu 24.04 against the built library (`results/<version>/ctypes.txt`).
- Every call in the table has a `false` answer. A `true` answer also keeps the input's other bits (`is_odd(17)` returned `0x11`); we did not test how callers handle that.
- Callers tested: C (gcc 14) and Python `ctypes`. Not C++, Go, other languages, or Rust code calling through a function pointer.
- Targets: per the fix, x86-64 System V targets other than Apple's. The fix changes only the System V code; the issue thread notes that the x86-64 UEFI target, which uses the Windows convention, already handled `bool` correctly. The reporter saw the value masked on aarch64 and loongarch64. **We tested only x86-64 Linux.**
- Versions: we tested 1.99.0 and 1.99.1. The change that exposed the bug ([#159317](https://github.com/rust-lang/rust/pull/159317)) merged on July 27, so nightly and beta toolchains from then until the fix reached them may also have it. The issue reproduces it on a nightly from October 5.
