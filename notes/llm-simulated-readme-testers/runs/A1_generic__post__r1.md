1. The README never says how to get the software. There is no download, clone or release instruction, and no repository link in the install flow. The `.env.example` also tells you to use `tools/rsa_key_generator.html` "on your computer", so a user who only has a hosting file manager has no clear way to obtain it. The Quickstart's "Upload `index.php`, `.htaccess`, `.env.example` to your subdomain" assumes you already have the files.

2. The Quickstart and the Set Up section disagree on the steps. Quickstart: "Upload `index.php`, `.htaccess`, `.env.example`... Rename `.env.example` to `.env`". Set Up: rename first, then "Upload `index.php`, `.htaccess`, and `.env`". The Quickstart also omits generating the keys and password hash, so a first-timer will upload the placeholder file and wonder why nothing works.

3. The "Minimum Requirements" demand "PHP 8.5" ("We live in the future now.") while the Introduction says it "will run on shared hosts, a Raspberry Pi, or any modern web server". Few shared hosts or distro repositories offer 8.5, and the page gives no way to check or install it. The sentence "This should include the following extensions by default" is vague about whether you need to check cURL and OpenSSL. The requirements list also gives no Apache module needs (`mod_rewrite`, `AllowOverride` for `.htaccess`) even though Apache is called the "default set up".

4. Key generation is the hardest mandatory step and is under-explained. The `.env.example` says "Newlines must be replaced with "\n"", but it does not say how to do that with the generated PEM output or whether the generator tool does it for you. A mistake here fails silently. It also does not explain why the key pair is needed or warn that the private key must be kept secret and backed up.

5. The password flow is confusing and partly misleading. `.env` needs a hash (`password_hash(...)` or `php tools/generate_password.php`), which requires PHP on your local machine. The API examples then send `"password": "your-password-here"`, and nothing says this is the plain password rather than the hash. The README claims "The password is encrypted when you send it and never stored on your server", which does not match what the examples show. They send it as a form field, so it depends on HTTPS. Hashes also contain `$` characters inside a double-quoted `.env` value, and the file does not say whether that is safe.

6. Writable directories and file protection are not explained for Apache. Step 7 says "Check your `data/logs/` directory", but no earlier step says this directory is created automatically or that PHP needs write permission. Only the Caddy page mentions permissions ("You may have to adjust the permissions of the directory..."). The README never says how `.env` and `data/` are kept from being downloaded on Apache, or tells you to test that `https://test.example.com/.env` is blocked. A leaked `.env` exposes the private key.

7. The verification steps give no expected result or troubleshooting. "Visit `https://test.example.com/.well-known/webfinger` and check that it shows a JSON file" does not say what the JSON should contain. WebFinger usually needs a `?resource=acct:...` query, so a bare visit may return an error that looks like failure. Later steps ("Follow your user", "Check your `data/logs/`") also say nothing about what success looks like or what to do if the follow never arrives.

8. The "Set Up" numbering is `0.` followed by repeated `1.` items. It will render oddly in some viewers, and the step count is unclear. The sentence "If you prefer, you can edit `index.php` and place the details in there" does not say where in `index.php` or in what format.

9. Hidden files are a trap for non-technical users. `.htaccess` and `.env` start with a dot, which many file managers and FTP clients hide or skip. The README does not warn about this or say how to confirm they were uploaded. The note "It will not work in a subdirectory" is good, but the page does not say what the symptom is.

10. The nginx and Caddy pages tell you to run `sudo apt-get install php php-curl` and then `php8.5-fpm`. On Debian and Ubuntu the `php` metapackage can pull in Apache, which conflicts with the web server you chose. The default repositories may not have `php8.5-fpm` at all, and no extra repository is mentioned. The `php-curl` package is installed but OpenSSL, which the README lists as required, is never mentioned. There is also no instruction on where to save the config, how to reload the server or how to enable the site.

11. The nginx example only has `listen 80;` even though the README says an HTTPS certificate is required. It does not explain how to add TLS. The nginx and Docker examples block `^/(.env|data)`, but the Caddy example blocks only `/.env` and `/php_errors.log`. It does not block `data/`, which holds logs, so Caddy users may expose log files.

12. The Docker page is called "Rough Docker Instructions" and is incomplete. The compose snippet is a fragment without `services:`. The `environment:` key contains only a comment. The Traefik comment says "Internal port for postiz", which looks copied from another project. The hostname alternates between `your.host.com` and `you.host.com`. The page never says where `index.php`, `.htaccess` and `.env` go in the mounted directory. It gives no `docker compose up` command, and the `nginx.conf` path and `fastcgi_pass 127.0.0.1:9000` are unexplained.

13. The test file for the nginx and Caddy pages is unhelpful. Visiting `test.php` directly leaves `$_GET["path"]` unset, so the output will be a warning or blank rather than the expected message. No expected output is given. Nothing tells you to delete `test.php` afterwards.

14. The API documentation is incomplete. The Features list promises unfollow, block, unblock and update-profile actions, but the API section only documents Follow and Move for `action/users`. No other action names or response formats are given, and no error codes or what a successful call returns. "Delete Post" needs a `guid` but never says where to find it. "You can send HTML. See `$allowed_elements`" points to a variable in the source without saying which file.

15. The image upload example is non-obvious. `files = [("1",("This is the alt text", open("red.png", "rb")))]` puts the alt text in the filename slot of the tuple. The text does not explain this or that the key names "1" to "4" are the required slot numbers. The multi-image example names its files "red", "green" and so on without saying whether those are alt text. The text says "up to four image files" but does not tie that to the slot names.

16. The location example looks wrong: `"longitude": 40.77563, "latitude": -73.97474` for the John Lennon Memorial. Those values are swapped (latitude is about 40.77 and longitude about -73.97 for New York), so a copied example would place the post in the wrong location.

17. The Python requirements are incomplete. "Requirements" only mentions Requests, but the Debugging section imports `requests_toolbelt`, which is a separate install. It does not say how to run the examples against a bot, or that `test.example.com` must be replaced with your own subdomain (a bare placeholder is used throughout).

18. The `.env.example` pre-fills optional values that go public if untouched. `REALNAME`, `SUMMARY` (linking to the project source), `BIRTHDAY` ("2024-02-29T12:34:56Z"), and four `PROFILE_NAME_n` and `PROFILE_VALUE_n` pairs including a mention of another person's account. A user who skips the optional section will publish those, and nothing says to blank them. `USERNAME="example"` is shown while the README uses `@username@test.example.com`.

19. Small inconsistencies in `.env.example`. One comment line is missing the `;` ("#	This is the joined date of your bot."). `MAX_LOGS=2048` is unquoted while `PAGE_SIZE="1000"` is quoted, which suggests but does not say whether quoting matters. `AVATAR` is "relative URl without leading slash", but the file never says where to upload the image. The optional `DID` and `NEW_NAME` fields point to external pages without explaining the steps in this project.

20. The migration instructions are hard to follow. "Then you will need to send a Move request to your ActivityBot" is followed by an example, but the order of steps (set `NEW_NAME`, upload `.env`, then POST `Move`, then act on the new account) is mixed across two paragraphs. The linked limitations page is the only guidance on what is lost.

21. Tone and noise in the install path. The requirements list includes jokes ("GLaDOS", "Wayland", "LLM"), and "Lenny" is probably meant to be Lemmy. The FAQ answer "Because I hate you and want you to suffer" and the long AI policy sit in the same README as the install steps. A first-timer scanning for what to do must read past them. The policy also says AI was not used, while the repository contains an `AGENTS.md`, which is confusing without explanation.

22. There is no upgrade, backup or uninstall guidance. A user cannot tell which files to keep (`.env`, `data/`) when replacing `index.php` with a new version. The repository has `CONTRIBUTING.md` and a `tests/` folder, but the README does not link to them or say how to run the tests.
