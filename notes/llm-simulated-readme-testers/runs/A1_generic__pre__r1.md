1. The README says to edit `index.php` for the username, password and keypair ("Edit the `index.php` file to add a username, password, and keypair"), but it never says what the variables look like, where in the file they go, or how to produce a keypair or password hash. The details are only in `.env.example`, which the README treats as an alternative ("If you prefer, you can rename `.env.example` to `.env`"). A new user has to guess which route is the primary one and has to read the code to find out.

2. The key generator is named inconsistently. `.env.example` says "Generate locally by opening `tools/rsa_keys.html`", but the file list shows `tools/rsa_key_generator.html`. The README never mentions the tool at all, so a user following `.env.example` will not find the file.

3. The credentials instructions give no way to check that the secrets are correct. `.env.example` says keys need "Newlines must be replaced with "\n"" and the password must be a hash from `password_hash(...)`. The README API examples use `"password": "your-password-here"` without saying that this is the plain-text password and that `PASSWORD` in `.env` holds only the hash. Pasting the hash into the API call, or the plain password into `.env`, is an easy mistake. The `.env.example` header also says only `KEY_PRIVATE, KEY_PUBLIC, PASSWORD, and USERNAME` are needed, while the README says nothing about which fields are required.

4. "PHP 8.5 (We live in the future now.)" is a very steep requirement for a project that claims "*everything* supports PHP. You can FTP these files onto any host". Most shared hosts and distro packages will not offer 8.5 yet. The README does not say why 8.5 is needed or whether older versions work. The joke obscures what is a hard blocker for many users. The same applies to the "Docker, Node, MongoDB, Wayland, GLaDOS, React, LLM, Adobe Creative Cloud, Maven (absolutely none of these!)" line. It is meant humorously, but it sits in a requirements list and takes a moment to parse as "not required".

5. The requirement list omits things the instructions rely on. The nginx page installs `php-curl`, but the README never lists curl as a requirement. The README requires Apache with `.htaccess` support and `mod_rewrite` ("The `.htaccess` file transforms requests...") and file-write permission on the web root, but neither is stated. Nor does it say that PHP must be able to create `/data/logs`, `/data/followers`, `/data/inbox`, `/posts` and `/quotes`.

6. The setup steps have a numbering and ordering problem. The list starts at "0." and then repeats "1." several times, which renders unpredictably across Markdown viewers. Step 4 is "Optionally, upload an avatar and banner image", but the `.env.example` guidance says these are relative paths set via `AVATAR`/`BANNER`, and the README does not say that. The README says `https://test.example.com/.well-known/webfinger` should show a JSON file, but real webfinger requires a `?resource=acct:...` query. It is not stated what to expect when visiting it bare, so a user cannot tell success from failure.

7. The `.env.example` header says "Then rename this file to .env and upload it along with index.php and .htaccess". Leading-dot files are hidden by default in many FTP clients and file managers, and the README never warns about this. There is also no warning that the web server must not serve `.env`. Only the nginx configs include `location ~ ^/(.env|data) { deny all; ...}`. For Apache, the user has to trust the `.htaccess` to do this, and the README does not confirm it. Since `.env` holds the private key, this matters.

8. The README is inconsistent about where data lives. "Post files are saved as .json in the `/posts` directory" and "Quote acceptance and stamps are saved as .json in the `/quotes` directory" use root-level paths, while logs, followers and inbox use `/data/...`. It is unclear whether `/posts` and `/quotes` are inside `/data`, and the nginx rules only deny `/data` and `.env`. That could leave posts and quotes browsable, which may or may not be intended.

9. The nginx and Docker guides are incomplete and in places wrong for a first-time user. `README_nginx.md` starts mid-thought ("requires php8.5-fpm which is a thing that passes requests to PHP"), has no HTTPS or certificate setup (`listen 80;`), and mixes `sudo apt-get install php php-curl` with a separate `php8.5-fpm` install, which does not exist in default Debian/Ubuntu repositories. The Docker guide has a copy-paste artefact ("Internal port for postiz"), uses `you.host.com` in one place and `your.host.com` in another, and does not show where `.env`, `index.php` or `.htaccess` go in the volume mapping. Its compose YAML has an empty `environment:` block with only a commented-out entry, which may fail to parse. It is also described as "Rough Docker Instructions" and "Documenting what I had to do", so the tone sets low expectations. The nginx config in `README_docker.md` ends with a stray closing code fence inside the file.

10. Several README items are internally contradictory or confusing about features. "Verify cryptographic signatures, including RFC 9421" is listed as supported, but "Sign messages with RFC 9421 Signatures" is listed as unsupported. The distinction between verifying and signing is not explained. "Receive messages (other than follows, unfollows, and quote requests)" is unsupported, yet the "How this works" section says "Messages sent to your inbox are saved as .json in the `/data/inbox` directory". The first-time user cannot tell what the bot actually does with incoming activity.

11. The API section has errors a user will hit when copy-pasting. In "Add a Location", the example uses `"longitude": 40.77563, "latitude": -73.97474`, which are swapped (40.77 is New York's latitude, and -73.97 its longitude). "Update / Edit Post" posts to `/action/send` with a `guid`, while "Delete Post" uses `/action/delete`. That is plausible, but it is never explained, and the way to find a post's `guid` is not documented ("You will need the ID of your post"). The media example uses the file-field name `"1"` with the alt text as the filename, an unusual and undocumented convention. "Requirements" lists only `requests`, but "Debugging" needs `requests_toolbelt`, which is not mentioned there. Sending the password in a plain POST body is shown without any note about HTTPS being required.

12. The `.env.example` has format problems. Line 48 reads `#	This is the joined date of your bot.` and is missing the `;` used by every other comment line, so it may be parsed as a different kind of line. The `BIRTHDAY` default of `2024-02-29T12:34:56Z` is a placeholder date that will become the bot's real joined date if left unchanged. `MAX_LOGS=2048` is unquoted while `PAGE_SIZE="1000"` is quoted, with no explanation of whether quoting matters. `SUMMARY` contains `<a href='...'>` with single quotes inside double quotes. "Relative URl" and "account URl" are typos for "URL". The `NEW_NAME` instruction ("POST a move message to the "action/users" endpoint") is vague without the example found only in the README.

13. The README's "Check your `/data/logs/` directory to see if the follow request was received correctly" is the only troubleshooting guidance. There is no description of what a good log looks like, what the common failures are (wrong key format, wrong PHP version, subdirectory install, missing `mod_rewrite`), or where PHP errors show up. The `README_nginx.md` ends with a `test.php` check that is never connected to the main setup flow and is not required in the main README.

14. There is no obvious install path for tests, contributors or tools. The file list includes `CONTRIBUTING.md`, `AGENTS.md`, `tests/` and `tools/generate_password.php`, but the README does not link to `CONTRIBUTING.md` (it directs people to the issue tracker instead) or explain how to run the PHP unit tests. `AGENTS.md` appears in the file list for a project whose README says no AI was used, and a user will wonder what it is. The README also contains a stale or confusing funding date ("From 2026-08") and a project URL (`gitlab.com/edent/activity-bot`) that a user cannot verify matches the repository they are reading.

15. The tone of some FAQ entries ("Because I hate you and want you to suffer.", "*sigh* If you must.", "Dunno. Try it and find out.", "you haven't sent a Pull Request") may put off newcomers and gives them no real guidance. The scaling and disk-space answers do not give numbers beyond "over a thousand followers" and "2,048 log files", and the "100MB free disk space" minimum is not tied to either. The "Multiple bots" answer ("You don't. Every bot needs its own domain name.") conflicts with the earlier "It will not work in a subdirectory" and the suggestion of subdomains, but never states that a subdomain is a valid way to run several bots on the same host.
