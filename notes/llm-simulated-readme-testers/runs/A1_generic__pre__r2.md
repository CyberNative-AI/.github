1. The Set Up section never says where to get the software. The files are presumably meant to come from a clone or download, but there is no clone URL, release link or "download index.php and .htaccess" step before "Upload `index.php` and `.htaccess` to the *root* directory of your domain."

2. Step 1 says "Edit the `index.php` file to add a username, password, and keypair", with `.env` offered only as an alternative ("If you prefer..."). The README never says which option wins if both are set, which variables or constants to edit in `index.php`, or that the password must be a hash rather than plain text. The .env.example comments tell the user to "rename this file to .env and upload it", so the two docs disagree about the primary path.

3. The README does not explain how to produce the required credentials. It never mentions `tools/rsa_key_generator.html` or `tools/generate_password.php`. The .env.example points to the wrong file name: "Generate locally by opening `tools/rsa_keys.html`". The file list shows `tools/rsa_key_generator.html`, so the user will look for a file that does not exist.

4. The password handling is confusing. .env.example says to store the output of `password_hash( "Y0ur_p4s5w0rd", PASSWORD_DEFAULT );` in `PASSWORD`, but every API example sends `"password": "your-password-here"`. Nowhere does it say that the hash goes in the config and the plain text goes in the API call. A newcomer is likely to paste the plain password into `PASSWORD`, or send the hash.

5. The key format is under-explained. "Newlines must be replaced with "\n"" gives no way to do that conversion, and the sample headers (`BEGIN RSA PRIVATE KEY` / `BEGIN PUBLIC KEY`) may not match what the generator emits. There is also no warning that the private key must never be served over HTTP.

6. The PHP requirement is very hard to meet and contradicts the pitch. "PHP 8.5 (We live in the future now.)" is a joke where a version requirement should be. It sits badly with the FAQ claim that "*everything* supports PHP. You can FTP these files onto any host and be guaranteed they'll run." Most shared hosts will not offer 8.5. The README does not say whether older versions work, or give a way to check.

7. The requirements omit things the setup relies on. Apache with `mod_rewrite` and `AllowOverride` is implied by `.htaccess` but never listed. The nginx README installs `php-curl`, which suggests curl is needed, but only OpenSSL is listed. The write permissions that the `data/`, `posts/` and `quotes/` directories need are not mentioned either.

8. The line "Docker, Node, MongoDB, Wayland, GLaDOS, React, LLM, Adobe Creative Cloud, Maven (absolutely none of these!)" sits in the requirements list as a joke. A first-time reader has to work out whether anything in it is a real requirement. It also precedes the Docker FAQ and a whole `README_docker.md`, which makes it look contradictory.

9. The "Check your `/data/logs/` directory to see if the follow request was received correctly" step assumes the user has file access and that the directory exists already. Other paths in "How this works" are inconsistent. Logs, followers and inbox are under `/data/...`, but posts are in `/posts` and quotes in `/quotes`. It is unclear whether these are relative to the web root, and it is unclear which are publicly reachable.

10. The webfinger check is probably wrong as written. "Visit `https://test.example.com/.well-known/webfinger` and check that it shows a JSON file with your user's details." WebFinger normally needs `?resource=acct:username@test.example.com`. Without it the user may see an error and think the install failed. No expected output or troubleshooting is given.

11. There is no troubleshooting or local-testing guidance. The service needs a public HTTPS subdomain, which means a failed set-up gives no feedback beyond a blank page. There is no list of common errors such as 500s, rewrite not working, permissions problems or a missing PHP extension. There is also no "what to do if Mastodon can't find the user".

12. Several README claims contradict each other. The "doesn't do" list says "Receive messages (other than follows, unfollows, and quote requests)", yet "How this works" says "Messages sent to your inbox are saved as .json in the `/data/inbox` directory". Both "Verify cryptographic signatures, including RFC 9421" (supported) and "Sign messages with RFC 9421 Signatures" (not supported) appear without explanation. "That's it!" follows a very long list. The feature list is hard to use as a guide to what to configure.

13. The API is documented only by Python examples, with no reference. There is no list of endpoints, parameters, required versus optional fields, or response and error formats. Listed features such as Unfollow, Block, Unblock, Show followers and Quote posts have no example, and the valid `action` values are never given. Only Python with `requests` is shown, and `requests_toolbelt` for the debugging snippet is not in "Requirements".

14. The media upload example is cryptic. `files = [("1",("This is the alt text", open("red.png", "rb")))]` places the alt text where a file name would normally go. The convention that the key is a position number and the first tuple element is the alt text is never explained. The multiple-image example uses "red", "green" and so on, which look like file names but would become alt text.

15. The location example appears to have latitude and longitude swapped. `"longitude": 40.77563, "latitude": -73.97474, "place": "John Lennon Memorial"` uses values that are New York's latitude and longitude the other way round. A user who copies it will get a wrong place.

16. The migration instructions are hard to follow. .env.example says `OLD_NAME`/`NEW_NAME` take "the full account URl" such as "https://new.example/users/username", but the README Move example posts `"user": "@new@example.com"`. The README says to "follow its procedure" on the other server without saying what that is. It is not clear which account to log in to at each step or in what order.

17. .env.example has a few small problems of its own. `BIRTHDAY` has a comment line with `#` instead of `#;`, a stray typo. `MAX_LOGS=2048` is unquoted while `PAGE_SIZE="1000"` is quoted, with no explanation of which style is expected. `AVATAR`/`BANNER` say "relative URl without leading slash" but not relative to what, or where to upload the file. The default `SUMMARY` links to someone else's project page ("Get the source code"), so it will point at the wrong place if copied.

18. The nginx guide is skeletal and has issues. "requires php8.5-fpm which is a thing that passes requests to PHP" is not instruction-grade wording. `sudo apt-get install php php-curl` can pull in Apache on Debian and Ubuntu, which conflicts with nginx. `php8.5-fpm` is not in default distribution repositories and no repository is given. The server block only has `listen 80;` with no HTTPS even though HTTPS is required. The `.env` deny rule `^/(.env|data)` has an unescaped dot and over-matches. It does not block `.htaccess` the way the Docker file's dotfile rule does. The `test.php` step has no stated expected output and no reminder to delete the file afterwards.

19. The Docker guide is labelled "Rough Docker Instructions" and has copy-paste leftovers. The Traefik comment says "Internal port for postiz", which is another project. The server name appears as both `your.host.com` and `you.host.com`. `environment:` contains only a comment, and the commented line uses `//` instead of `#`. There are no steps to create the `.env`, to set permissions for the data directories or to start the stack. Mounting `/var/www/html/public` means data and posts are written into the public web root. A mounted `conf.d` file may clash with the image's own "Default server definition". The bot also never gets a TLS setup unless the user adds Traefik.

20. The repository contains `AGENTS.md`, but the README's AI policy says "AI was not used at any stage of the construction of this software." `CONTRIBUTING.md`, `tests/` and `agpl-3.0.txt` are never linked from the README. A first-time user cannot tell what `AGENTS.md` is for, or how to run the tests.

21. The tone of the FAQ hides practical answers. "Because I hate you and want you to suffer." and "*sigh* If you must." are the replies to the PHP and Docker questions, which makes them harder to take at face value. The answer to "How do I run multiple bots with this?" is "You don't. Every bot needs its own domain name." The suggested workaround of free subdomains is explained only briefly. "Will this scale...?" answers "Dunno."

22. The disk and log guidance is incomplete. The README lists "100MB free disk space" and says "Probably not" to filling the disk, and `MAX_LOGS` caps only the number of log files. Followers, inbox, posts and uploaded media are not capped or mentioned, so the 100MB figure may be misleading for an active bot.

23. Minor formatting problems make the README harder to read. The setup list uses "0." then repeated "1." items. The text "an `.htaccess file`" has its backticks in the wrong place. The Funding section's "From 2026-08" wording is unclear. There is no table of contents for a long README.
