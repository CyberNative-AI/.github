## PROBLEMS

1. The Quickstart and the Set Up section disagree about the order of operations. Quickstart says "Upload `index.php`, `.htaccess`, `.env.example` to your subdomain" then "Rename `.env.example` to `.env`", while Set Up says to rename and edit first, then "Upload `index.php`, `.htaccess`, and `.env`". Following the Quickstart leaves a file containing secrets on the server under a predictable name until it is renamed.
2. There is no instruction for obtaining the files. Neither README says where to download them or how (clone, ZIP, release), and the Quickstart's three-file upload list leaves out `tools/`, which the setup depends on.
3. `tools/rsa_key_generator.html` and `tools/generate_password.php` are required by `.env.example` but not mentioned in the README Set Up steps, and the Quickstart's file list omits them.
4. "Newlines must be replaced with "\n"" is ambiguous. It doesn't say whether the generator already outputs this form, how to convert a multi-line key by hand, or what the correct single-line result looks like. The placeholder `-----BEGIN RSA PRIVATE KEY-----\n...\n-----END RSA PRIVATE KEY-----` isn't shown filled in, and nothing says that the generated key's header must match it.
5. Password creation assumes PHP on the user's own computer: "Generate with `password_hash( "Y0ur_p4s5w0rd", PASSWORD_DEFAULT );`" and "run on the command line `php tools/generate_password.php 'Y0ur_p4s5w0rd'`". There is no alternative for people without local PHP, and the first form is a bare PHP expression that does not run on its own. The single-quote command example also fails in Windows cmd.exe.
6. The password hash contains `$` characters, and there is no guidance on quoting or escaping it in `.env` (including for Docker/compose environments, where `$` can be interpolated).
7. The README doesn't say that the `password` value in the API examples (`"password": "your-password-here"`) is the original plain-text password, not the hash stored in `.env`.
8. "The password is encrypted when you send it and never stored on your server." is confusing and at odds with the setup: a bcrypt hash is stored in `.env`, and the API examples send the password as a plain form field, so only HTTPS protects it in transit. The sentence needs to say what actually happens.
9. "Minimum Requirements" demands "PHP 8.5 (We live in the future now.)" with no way to check the host's version, no note on what happens on older versions, and no guidance on what to do if a shared host does not offer 8.5. This conflicts with the claim that it "will run on shared hosts, a Raspberry Pi, or any modern web server".
10. "This should include the following extensions by default" is vague. It doesn't say how to check that cURL and OpenSSL are enabled, and the nested bullets make it unclear whether the list is a requirement or a description of a default install.
11. The nginx and Caddy pages install `sudo apt-get install php php-curl` and then `sudo apt-get install php8.5-fpm`. On most distributions `php`/`php-curl` install the distribution's default PHP version (not 8.5), the `php` package may pull in Apache and conflict with nginx/Caddy for ports 80/443, and `php8.5-fpm` usually needs an extra package repository that isn't mentioned. The cURL extension is also never installed for 8.5 specifically.
12. "Create a new subdomain on your web host" assumes the user has a domain and a host. There is nothing for Raspberry Pi/home hosting (DNS, port forwarding, dynamic DNS, getting a certificate), even though "a Raspberry Pi" is named as a supported target. Nor is there any explanation of how to choose the subdomain's document root, or whether the apex domain can be used.
13. "It will not work in a subdirectory." and "the *root* directory of your subdomain" are not explained for control panels (what to enter as the document root), and the FAQ's "Every bot needs its own domain name" sits uneasily with the Introduction's "subdomain" framing.
14. Dotfiles (`.env`, `.env.example`, `.htaccess`) are hidden in many file managers and FTP clients, and Windows Explorer will not let a user type a name that starts with a dot. The README says nothing about this.
15. For Apache, the README doesn't say that `.htaccess` needs `mod_rewrite` and `AllowOverride` enabled, nor what to do on hosts that don't read `.htaccess` (LiteSpeed, IIS, etc.). The `.htaccess` file's role is never stated.
16. Default `.env.example` values for optional fields are live defaults: `SUMMARY="<a href='https://gitlab.com/edent/activity-bot/'>Get the source code</a>!"`, `BIRTHDAY="2024-02-29T12:34:56Z"`, and `PROFILE_NAME_1` to `PROFILE_VALUE_4` (including an example mention of the author's own account). The file doesn't warn that leaving them in place publishes them on the user's bot, or say how to remove a profile field.
17. The comment formatting in `.env.example` is inconsistent. `#;` is used almost everywhere but one line is just `#	This is the joined date of your bot.`, and the file doesn't explain why `#;` is used at all.
18. "If you prefer, you can edit `index.php` and place the details in there." doesn't say where in `index.php`, which variables, or how to write the multi-line keys there.
19. The webfinger check is underspecified: "Visit `https://test.example.com/.well-known/webfinger` and check that it shows a JSON file with your user's details." The real endpoint normally takes a `resource=acct:...` parameter. There's no example URL, no example output, and no troubleshooting for 404, 500, a blank page or a download prompt.
20. There is no troubleshooting section or error log location in the main README. `php_errors.log` appears only in the Caddy config and `data/logs/` only in step 7, so a user whose setup fails has no place to look.
21. "Check your `data/logs/` directory to see if the follow request was received correctly." doesn't say that `data/` is created automatically on first run (only the Caddy page hints at this), that the web user needs write permission to the install directory, which file to look for, or what a success entry looks like. Step 6 also doesn't say whether the follow should be accepted automatically or how to confirm it from the Mastodon side.
22. The Caddy configuration blocks only `/.env` and `/php_errors.log`, while the nginx configurations also deny `^/(.env|data)`. It looks as though Caddy users are left with `data/` (logs and anything else stored there) publicly reachable. The README never says what must be kept private.
23. The permissions advice is vague and inconsistent. Caddy says "You may have to adjust the permissions of the directory ActivityBot is installed in", the nginx page says nothing, and the Docker page doesn't mention bind-mount ownership for the container's unprivileged user.
24. The nginx page shows a config in a block labelled `bash`. It doesn't say where the file goes, how to enable it or reload nginx, and it only has `listen 80;` even though HTTPS is required, with no certificate setup (certbot, TLS block).
25. The `test.php` check in both nginx and Caddy pages doesn't test the rewrite rules, because an existing file is served directly. `echo $_GET["path"];` also raises an undefined-key warning when the page is requested with no query string, expected output isn't stated, the page says "Then access it at `https://test.example.com/test.php`" even though the nginx config only listens on port 80, and the page never says to delete `test.php` afterwards.
26. README_docker.md is described as "Rough Docker Instructions." and "Documenting what I had to do". The compose snippet is only a fragment (no `services:` key or networks), `environment:` has only a commented-out entry (`# PHP_OPCACHE_ENABLE: "1"   // Increase performance`, whose `//` is not comment syntax) and may be rejected as empty, and the Traefik label says "Internal port for postiz", copied from another project.
27. The Docker page uses different placeholder hostnames (`your.host.com`, `you.host.com`, and `test.example.com` elsewhere), doesn't say which files belong in the mounted `/path/to/your/docker/stuff/activity-bot/` directory, doesn't say how the mounted `activity-bot.conf` relates to the image's own default server on 8080, gives no command to start the stack, and says nothing about HTTPS if the user isn't using Traefik. It also links neither to the ServerSideUp documentation it says it borrows from, nor to the main README's key and password steps.
28. The Quickstart says to "follow the instructions inside" `.env.example`, which says to "rename this file to .env and upload it". The Quickstart already says to rename, and Docker users don't "upload" at all, so the instructions overlap and conflict.
29. "Optionally, upload an avatar and banner image to make the user look nice. Edit `.env` to include the image locations." doesn't explain that the path is relative to the web root, nor that the profile must then be pushed to followers via the "Update Account" API call, which is documented far lower down (in "Using the API") and isn't linked from step 8. The `.env` also says "Should be a relative URl without leading slash", which clashes with the instruction to "upload" images in a place never specified.
30. The Set Up list never ends with posting a first message, so "working setup" is undefined. The API section's "Check it has worked" subsection is separated from the Set Up steps and comes after several other examples.
31. The API section assumes Python and the Requests library, with no curl example for users who just want to test with a command line, and `requests_toolbelt` (used in "Debugging") is not listed under "Requirements".
32. "You can send HTML. See `$allowed_elements` to see which ones are supported." doesn't say which file contains `$allowed_elements`.
33. The location example swaps coordinates: `"longitude": 40.77563, "latitude": -73.97474`. Those values read as latitude 40.77 and longitude -73.97 (New York), so the post would be placed in the wrong location if copied.
34. Delete and edit examples say "You will need the ID of your post" and "You will need the ID of your post" but never say where to find a GUID (website HTML, logs, response body of the send request). The example GUID is just a made-up string.
35. The image-upload examples put alt text in what looks like the filename slot of a `requests` file tuple (`("1",("This is the alt text", open("red.png", "rb")))`). The multi-image example uses `("red", ...)`, `("green", ...)` and doesn't say whether these are alt text, so the convention is unclear.
36. The "Migrate Accounts" section has a typo ("acount") and is sequenced confusingly. It says to add `OLD_NAME` or `NEW_NAME` to `.env`, then "follow its procedure", and for moving away, "Once your new acount is set up, go to your new account and follow its procedure for moving followers to it", before "Then you will need to send a Move request". The order of steps and which account performs which action is hard to follow, and `OLD_NAME`/`NEW_NAME` require "the full account URl" (also typo'd) without a link to an example.
37. The Bluesky bridge is listed as a feature ("Bridge to BlueSky with your domain name via Bridgy Fed") and `.env.example` has a `DID` field, but the README gives no steps for doing the bridging.
38. The FAQ says disk usage is "Probably not" a problem, while `.env.example` warns that logs "can fill up *fast*" and "can exhaust your file limits", and the Minimum Requirements say "Expect lots of logs". The guidance on `MAX_LOGS` is split between three places and sounds contradictory.
39. The README presents typos in user-facing text, such as "URl" for URL in several places, which makes searching for these terms harder and reduces confidence in the instructions.
