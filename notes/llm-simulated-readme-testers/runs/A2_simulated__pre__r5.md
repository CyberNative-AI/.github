# Simulated walkthroughs of the ActivityBot README

## Person 1: Priya, hobbyist on cheap shared hosting (cPanel, Apache, FTP)

"A bot server in one PHP file, great, I can do that. Minimum requirements: PHP 8.5. My host's selector tops out at 8.3. Is 8.5 even out on shared hosting? It says 'We live in the future now', which is cute but doesn't tell me what to do. The FAQ says 'everything supports PHP' and I'd be 'guaranteed they'll run', which contradicts the requirement. I'll try anyway.

Set Up step 0: I make a subdomain. Step 1: 'Edit the index.php file to add a username, password, and keypair.' Keypair? I open index.php and there's a lot of code. I don't know which lines to change or whether the password goes in as plain text or as something hashed. The README doesn't say how to make a keypair. The alternative is a `.env`, so I rename `.env.example`. Except my FTP client and cPanel hide dotfiles, so I can't see it to rename it. After a long detour I find the comments in the file: keys come from `tools/rsa_keys.html`. There's no such file in the download. There's a `tools/rsa_key_generator.html`. I guess that's it. It gives me a key, but the file wants one line with `\n` in place of newlines. Did the tool already do that? I can't tell. The password needs `php tools/generate_password.php`, and I have no PHP on my laptop. The other option is `password_hash(...)`, which also needs PHP.

I upload `index.php`, `.htaccess` and `.env` to 'the root directory of your domain'. Is that public_html or the subdomain's folder? Then I visit `/.well-known/webfinger` and get an error. It says 'a JSON file with your user's details', but I don't know what the correct output looks like, or whether it needs a `?resource=` parameter. I can't tell whether the bug is my PHP version, mod_rewrite, or my `.env`. There's no troubleshooting section and no 'check your PHP version' step. I give up and email the host about PHP 8.5."

## Person 2: Marcus, sysadmin with an Ubuntu VPS and nginx

"I'll skip the Apache steps and go to the FAQ link for nginx. `README_nginx.md` says it 'requires php8.5-fpm'. The first command is `sudo apt-get install php php-curl`. On Ubuntu that pulls the distro's default PHP and likely Apache, which grabs port 80 and fights nginx. Then `apt-get install php8.5-fpm` says no such package, because it's not in the stock repos. There's no mention of a third-party PHP repo. I add one myself.

The nginx config has `listen 80;` only. The main README says HTTPS is required. There's no certbot step or 443 block. I don't know where the config goes (sites-available? conf.d?) or that the `map` block must sit in the `http` context. There's no `nginx -t`, reload, or symlink step. `root /var/www/test.example.com/;` doesn't say who owns that directory. The bot needs to write `/data` and `/posts`, so PHP-FPM's user needs write access, and nothing says that. The comment 'I don't THINK these are needed but computers are oh so very confusing' makes me doubt whether the config is tested.

Test step: I create `test.php` and visit it. It prints 'Path is...' and probably a warning about an undefined `path` key. I don't know what success looks like. Nothing tells me to delete `test.php` afterward. I'm also not sure which main-README steps still apply. The Set Up section says upload `.htaccess`, which does nothing here. The `.env` deny rule is in the nginx config, but the README never tells me to check that `https://…/.env` returns 404. My private key lives in that file, so I check it by hand."

## Person 3: Dana, homelab user with Docker Compose and Traefik

"I jump to `README_docker.md`. It says 'Rough Docker Instructions'. The compose snippet has no `services:` line, no `docker compose up` step, and `environment:` has only a commented-out entry. That's an empty mapping and may fail validation. The comment 'Internal port for postiz' is clearly pasted from another project. The Traefik rule says `your.host.com` but the nginx config says `server_name you.host.com;`. Are those meant to match?

Volumes: I mount a directory to `/var/www/html/public` and a conf file to `/etc/nginx/conf.d/activity-bot.conf`. The doc doesn't say that the conf file is the config pasted below, or that `index.php` and `.env` go in the mounted directory. The 'Default server definition' on port 8080 might clash with the image's own default server. The container user probably can't write to my bind mount, so `/data` won't be created and there's no note on ownership. Behind Traefik, the bot sees plain HTTP. Does ActivityBot need forwarded-proto headers to build correct `https://` IDs? The README doesn't mention it.

I read the main README for the `.env` bits and see Docker listed under 'absolutely none of these!' in Minimum Requirements. The FAQ says 'If you must'. Fine, I'm doing it anyway, but I can't tell what success looks like beyond the generic follow test."

## PROBLEMS

1. The `.env.example` header says "Generate locally by opening `tools/rsa_keys.html`", but the repository file is `tools/rsa_key_generator.html`. The README itself never mentions the tool or how to produce the keypair.
2. Setup step 1, "Edit the `index.php` file to add a username, password, and keypair.", doesn't say where in `index.php` the values go. It doesn't say whether the password is plain text or the hash, or how to generate either. The key and password-hash instructions live only in `.env.example`, which the README presents as an optional alternative.
3. The README and `.env.example` disagree about where configuration lives. Step 1 treats `index.php` as primary and `.env` as an option, while "How this works" says "The `.env` file contains all the settings and secrets for your bot." Optional settings such as `AVATAR`, `OLD_NAME` and `NEW_NAME` are documented only for `.env`, so an `index.php` user can't tell how to set them.
4. The key format is under-specified. `.env.example` says "Newlines must be replaced with "\n"", but nothing says whether the HTML generator already outputs that format. Nothing warns that the `$` characters in a `password_hash` value may be mangled in a `.env` file, or tells the reader whether to quote the value.
5. The password tools need PHP on the user's own machine (`php tools/generate_password.php 'Y0ur_p4s5w0rd'` or `password_hash( "Y0ur_p4s5w0rd", PASSWORD_DEFAULT );`). The README never says PHP CLI is needed locally, offers a no-PHP route, or says that `tools/` should not be uploaded. The generated private key is also never marked as something to keep off the server's public paths.
6. "PHP 8.5 ... (We live in the future now.)" gives no help for hosts that don't offer 8.5, such as how to check the version or what to do if it's too old. The FAQ line "*everything* supports PHP. You can FTP these files onto any host and be guaranteed they'll run." contradicts the requirement.
7. Minimum Requirements omits things the setup depends on. It doesn't mention Apache `mod_rewrite` or `AllowOverride` for `.htaccess`, or write permission on the web root for `/data`, `/posts` and `/quotes`. It doesn't mention the `curl` extension either, even though `README_nginx.md` installs `php-curl`.
8. Dotfiles are a problem for upload. Step 1 says to rename `.env.example` to `.env` and upload `.htaccess`, but many FTP tools, file managers and Windows/macOS setups hide or mishandle dotfiles. No guidance is given on this.
9. The README doesn't tell the user to verify that `.env` and `/data` are not publicly downloadable. Only the nginx and Docker configs contain deny rules, and a leaked `KEY_PRIVATE` is serious.
10. The nginx and Docker alternatives are linked only from the FAQ at the bottom. The Set Up steps are Apache-specific ("upload `index.php` and `.htaccess` to the *root* directory of your domain"), so nginx and Docker users have no signal at the start that a different path applies and which steps still apply.
11. "Upload ... to the *root* directory of your domain" is ambiguous on shared hosting, where the account's `public_html` and a subdomain's document root differ.
12. The webfinger check, "Visit `https://test.example.com/.well-known/webfinger` and check that it shows a JSON file with your user's details.", shows no example of the expected output. It doesn't say whether the URL needs a `?resource=acct:...` parameter, and it doesn't say what common failures look like.
13. Step 5 says to search for "`@username@test.example.com`" without saying that `username` is the `USERNAME` value. It doesn't say that the domain must exactly match the host the bot is served from.
14. Step 7, "Check your `/data/logs/` directory to see if the follow request was received correctly.", doesn't say where that path is relative to. It doesn't say whether the directory is created automatically or what a successful log entry looks like. The "Follow your user" step also doesn't say what the user should see in Mastodon (for example, an immediate accepted follow).
15. The storage paths are inconsistent and unexplained. "How this works" lists `/data/logs`, `/data/followers` and `/data/inbox` but also top-level `/posts` and `/quotes`. It's unclear which are created automatically and which must be public.
16. The "How this works" note "Messages sent to your inbox are saved as .json in the `/data/inbox` directory." sits oddly next to "❌ Receive messages (other than follows, unfollows, and quote requests)". It's unclear what actually ends up in the inbox.
17. There is no troubleshooting section anywhere. Failure modes with no guidance include webfinger errors, no search result in Mastodon, and an empty log directory. Nothing is said for self-hosters behind NAT or tunnels, who have no public HTTPS endpoint.
18. The README says "Expect lots of logs" in Minimum Requirements, but the FAQ says "Will this fill up my disk? Probably not." The two messages pull in opposite directions, and `MAX_LOGS` is not mentioned in the README body.
19. Step 4 says "Optionally, upload an avatar and banner image to make the user look nice." It doesn't say that `AVATAR` and `BANNER` must be set in `.env` (relative paths, no leading slash, size limits). The same applies to `FAVICON`, which appears only in `.env.example`.
20. The API section assumes Python only. "Requirements" says "This assumes you have a modern version of Python and have installed the popular Python Requests library" with no install command and no `curl` or non-Python example, despite "you can use whichever language you want". The Debugging snippet also needs `requests_toolbelt`, which is never listed as a requirement.
21. The API examples never say what a successful response looks like, such as the status code, the body, or whether the new post's `guid` is returned. "You will need the ID of your post:" for delete and edit doesn't explain where to find it.
22. `"password": "your-password-here"` doesn't say that this is the plain password rather than the stored hash. `test.example.com` placeholders are also never explained as needing replacement.
23. The location example has latitude and longitude values swapped: `"longitude": 40.77563, "latitude": -73.97474`. Anyone copying it posts an invalid or wrong location.
24. "You can send HTML. Only formatting elements are allowed." doesn't list which elements or attributes are allowed. Other statements, such as "Autolink URls, hashtags, and @ mentions" and "Accurate support for converting user's text to HTML" under what the bot doesn't do, leave the actual behavior unclear.
25. The image example `files = [("1",("This is the alt text", open("red.png", "rb")))]` puts the alt text in the filename slot of the tuple without saying so. The multi-image example uses "red", "green" and so on, and doesn't say whether they are alt texts.
26. The feature list advertises Unfollow, Block, Unblock, Show followers, quote posts and viewing hashtags, but the API section documents only Follow and Move. The action names and parameters for the rest are missing.
27. "Update / Edit Post" posts to `/action/send` with a `guid`, while delete has its own endpoint and "Update Account" is a separate section with a similar name. The README doesn't explain that sending to the same endpoint with a `guid` means edit.
28. The migration instructions are vague. "go to your old account and follow its procedure for migrating away" and "go to your new account and follow its procedure for moving followers to it" give no order of operations or link. They don't say whether to do this before or after the bot is reachable, and "new acount" is misspelled.
29. `NEW_NAME`, `OLD_NAME` and the Move example disagree on format. `.env.example` asks for a "full account URl" such as "https://new.example/users/username", but the Move request sends `"user": "@new@example.com"`.
30. `README_docker.md` is called "Rough Docker Instructions" and the compose snippet is incomplete. It has no `services:` key, no `docker compose up` step, and an `environment:` key that contains only a comment, with a `//` note inside a YAML comment line.
31. The Docker doc has copy-paste leftovers and inconsistencies. "Internal port for postiz" comes from another project, and the Traefik host is `your.host.com` while the nginx block uses `server_name you.host.com;`. Neither is flagged as something to change consistently.
32. The Docker doc doesn't say what to put in the mounted `activity-bot.conf`, or that it's the nginx block below. It doesn't say that `index.php` and `.env` belong in the mounted public directory. It doesn't address whether the `listen 8080` "Default server definition" conflicts with the image's own default server.
33. The Docker doc doesn't mention bind-mount ownership and write permission for `/data`, `/posts` and `/quotes`. It also doesn't mention TLS being terminated at Traefik and whether the app needs forwarded headers to build `https://` URLs.
34. `README_nginx.md` says "requires php8.5-fpm" but its first command is `sudo apt-get install php php-curl`. That installs the distro's default PHP, and on Debian/Ubuntu may also pull in Apache. It doesn't mention that `php8.5-fpm` isn't in stock repositories and needs an extra repo.
35. The nginx example only has `listen 80;`, although the README requires HTTPS. It gives no certificate or 443 setup. It also doesn't say where to place the file, that the `map` belongs in the `http` context, how to enable it, or to run `nginx -t` and reload.
36. The nginx test step, "to test the config, make a file `test.php`" and "...and attempt to access it on test.example.com/test.php.", doesn't say what output is expected. The script echoes `$_GET["path"]`, which is not set when the file is requested directly. It doesn't say to delete `test.php` afterward. The comment "I don't THINK these are needed but computers are oh so very confusing" undermines confidence in the config.
37. The Minimum Requirements bullet "Docker, Node, MongoDB, Wayland, GLaDOS, React, LLM, Adobe Creative Cloud, Maven (absolutely none of these!)" lists Docker as not needed while a Docker guide exists. The joke list can also be read as a prohibition, and it doesn't separate real requirements from jokes.
38. Minor text issues add friction: "an `.htaccess file`" has stray formatting, "URl"/"URls" is misspelled throughout, the setup list numbering starts at 0 and then repeats "1.", and one `.env.example` comment line starts with `#` while all the others start with `#;`.
